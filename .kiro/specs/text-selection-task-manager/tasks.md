## 0. 执行策略与阶段划分

### 0.1 推荐实施阶段

- **Phase 1: MVP 核心闭环**
  - 覆盖范围：1、2、3、4、5、6、7、8、9、16、17 中与基础能力直接相关的任务
  - 目标：实现“全局划词 -> Popup -> 保存 -> 主窗口查看/搜索/管理 -> 托盘后台运行”的最小可用闭环
  - 完成标准：需求 1、2、3、4、5、6、7、8 的核心验收条件可跑通，浏览器 mock 模式与 Tauri 模式都可联调

- **Phase 2: 增强生产力能力**
  - 覆盖范围：10、11、12、13、14
  - 目标：补齐 OCR、AI 建议、桌面便利贴、全局搜索台、提醒通知
  - 完成标准：需求 9、10、11、12、13 可用且具备降级策略

- **Phase 3: 扩展性与交付完善**
  - 覆盖范围：15、17.3、17.4、17.5
  - 目标：完成插件系统、跨平台回归、自动更新与交付文档
  - 完成标准：需求 14 可用，构建发布链路与回归清单完备

### 0.2 推荐开发顺序

- 先完成前端/后端共享类型、存储层和 mock 层，再做 UI 壳子
- 先打通 `text-selected -> Popup -> save_item -> items-changed -> Inbox 刷新` 主链路，再扩展 OCR/AI/插件
- 先在浏览器 mock 模式验证主要界面和交互，再切到 Tauri 真环境验证系统能力
- 先实现无插件、无 AI、无 OCR 的降级基础版本，再增加可选增强模块

### 0.5 高风险前置约束

- **全局划词监听**
  - 风险：跨平台实现差异大，浏览器/本地应用能力边界不同
  - 约束：优先确认 Windows 首发实现路径，macOS/Linux 可先保留兼容层与降级说明

- **来源与上下文捕获**
  - 风险：非浏览器应用很难稳定拿到 URL/标题/全文上下文
  - 约束：先保证 `unknown`/空上下文的降级链路完全可用，再逐步增强浏览器场景

- **OCR**
  - 风险：依赖 Tesseract 本地安装、语言包、性能与打包方案
  - 约束：先定义开发环境安装说明和运行时探测逻辑，再接入正式流程

- **AI 分析**
  - 风险：接口不稳定、超时、费用、响应结构不一致
  - 约束：必须先完成无 AI 的完整 Popup 体验，AI 仅作为可选增强层

- **插件系统**
  - 风险：运行时隔离、错误传播、插件协议演进成本高
  - 约束：先只支持受控 manifest + 受限扩展点，避免一开始开放过大的执行面
